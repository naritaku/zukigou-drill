# レビュー観点

`/local-review` や PR レビューで使う観点。**MUST** は必ず指摘する、**SHOULD** は指摘して
対応可否を判断する、**MAY** は軽微。偽陽性かどうかを自分で確かめてから挙げること。

## 1. 機能性・正確性

- MUST — ロジックの誤り / 未処理の例外 / 終了条件の無いループ / 仕様の実装漏れ / テスト失敗
- SHOULD — エッジケース未対応、状態遷移の矛盾、入力バリデーションの不足
- MAY — より良いアルゴリズムの余地

## 2. セキュリティ

- MUST — XSS（HTML エスケープ漏れ）/ 認証・認可の不備 / 機密情報のハードコードやログ流出 /
  ユーザー入力の検証欠落
- SHOULD — 最小権限の原則違反、監査ログの不足

このアプリ固有: API キーは必ずハッシュ化してから Firestore の ID やログに出す。IP は
`DAILY_IP_SALT` 付きのハッシュにする。`X-Forwarded-For` の採用位置を誤ると IP 別クォータを
回避できてしまう。

## 3. コード品質・保守性

- MUST — 規約違反（CLAUDE.md）/ 意味の分からない名前 / 50 行を超える関数 / 重複コード
- SHOULD — 複雑なロジックに説明が無い、型ヒント不足、責務が不明確、マジックナンバー
- MAY — スタイルの不統一（`ruff check .` が拾う範囲は指摘しない）

## 4. テスト

- MUST — テストが落ちている / 新しい分岐にテストが無い / 常に成功する形骸化したテスト
- SHOULD — エッジケースとエラー経路のテストが無い

`python -m unittest` は Gemini をモックするので**判定精度は見ていない**。精度は
`scripts/run_judgment_eval.py`（`docs/EVALUATION.md`）の担当。混同しないこと。

## 5. ドキュメント

- MUST — 手順が実装と食い違う / 新しいエンドポイントや環境変数が未記載
- SHOULD — セットアップ手順が不明確、図や例が不足

環境変数を足したら `docs/DEVELOPMENT.md` と `.github/workflows/deploy-cloud-run.yml` の
両方に反映されているか確認する（片方だけ、が起きやすい）。

## 6. パフォーマンス

- MUST — メモリリーク / ループ内での外部 I/O
- SHOULD — O(n²) 以上の計算量、大量データでのメモリ溢れ

このアプリ固有: **ロックを保持したまま外部 I/O を待っていないか**。同期エンドポイントは
anyio 既定 40 スレッドを共有するので、レスポンス経路に足す I/O は数を意識する。

## 7. 依存関係・環境

- MUST — サポート外の Python バージョン前提、未宣言の依存
- SHOULD — バージョン指定が緩い、非推奨パッケージ

## 8. 設定・環境変数

- MUST — 秘密情報のハードコード、設定の記載漏れ、本番と開発で挙動が変わるコード
- SHOULD — デフォルト値の妥当性、設定値のバリデーション不足

## 9. 破壊的変更

- MUST — 環境変数の削除・改名 / API レスポンス形式の変更 / エンドポイント削除 / 必須パラメータの追加
- SHOULD — デフォルト値の変更、戻り値の型変更、関数シグネチャの変更

環境変数を改名したら、既にデプロイ済みかどうかを確かめる。未マージなら影響なし、
デプロイ済みなら旧名のフォールバックか移行手順が要る。

## 10. デッドコード・未使用定義

- MUST — 呼ばれない関数 / 参照されない変数 / 使われない import / 削除済み機能の残骸
- SHOULD — 到達不可能なコード、デバッグコードの残存

例: `MODEL = os.environ.get(...)` を定義したのに `_gemini_models()` しか使われていない、
`if not models:` が常に偽で到達しない、など実際に見つかった型。

## 11. ログ・観測性

- MUST — 重要なイベントのログが無く障害を追えない / 本番で DEBUG ログが出る
- SHOULD — 相関 ID が無い、エラーの文脈情報が足りない

**監視指標は「今の状態」ではなく「累積」で持てているか。** 成功した 1 リクエストで
値が正常に戻る指標は、部分障害を隠す（`/readyz` の `quota_fallbacks` はこの理由で入れた）。
リトライやスキップの理由がログに出ているかも見る。

## 12. API 設計

- MUST — エラーレスポンス形式の不統一 / 不適切なステータスコード / パラメータ名の揺れ
- SHOULD — エラーメッセージが不明確

`detail` は機械可読な識別子（`rate_limited`、`daily_quota_exceeded`）にし、利用者向けの
文言はフロントで組み立てる。サーバー障害を利用者起因のエラーと同じコードで返さない
（`unavailable` を 404 で返すとフロントが「期限切れ」と誤案内する）。
