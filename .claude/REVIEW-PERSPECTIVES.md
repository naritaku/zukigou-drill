# Code Review Perspectives - レビュー観点の定義

定期的なコードレビュー時に確認すべき観点と、Issue 化の基準を明確にしたドキュメントです。

---

## 📋 レビュー観点一覧（全 12 観点）

### 1. 機能性・正確性

**観点**: コードが期待通りに動作するか

#### MUST（Issue 化必須）
- [ ] ロジックエラー：計算結果が正確でない
- [ ] 未処理例外：エラーハンドリングがない
- [ ] 無限ループ：終了条件がない
- [ ] 不完全な実装：仕様の一部が実装されていない
- [ ] テスト失敗：ユニットテストが失敗

#### SHOULD（Issue 化推奨）
- [ ] エッジケース未対応：特殊な入力に未対応
- [ ] 状態管理の誤り：状態遷移に矛盾
- [ ] 不完全なバリデーション：入力チェックが不足

#### MAY（軽微）
- [ ] パフォーマンス最適化の余地
- [ ] より良いアルゴリズムの存在

**レビュー方法**:
```bash
python3 -m unittest -v
```

---

### 2. セキュリティ

**観点**: セキュリティ脆弱性がないか

#### MUST（Issue 化必須）
- [ ] SQL インジェクション：クエリに直接入力値を埋め込み
- [ ] XSS 脆弱性：HTML エスケープなし
- [ ] 認証・認可の誤り：アクセス制御の不備
- [ ] 機密情報の露出：パスワード・キーのハードコード
- [ ] 入力検証の不備：ユーザー入力の検証なし
- [ ] セッション管理の誤り

#### SHOULD（Issue 化推奨）
- [ ] 最小権限の原則違反
- [ ] 暗号化不足：重要データが暗号化されていない
- [ ] ログの不足：監査ログがない

**レビュー方法**:
```bash
grep -r "eval\|exec\|pickle" main.py
grep -r "password\|secret\|api_key" main.py
```

---

### 3. コード品質・保守性

**観点**: コードが読みやすく保守しやすいか

#### MUST（Issue 化必須）
- [ ] コード規約違反：AGENTS.md に反する
- [ ] 名前付けが不適切：変数名が意味不明
- [ ] 過度な複雑性：関数が長すぎる（>50行）
- [ ] 重複コード：同じロジックが複数回
- [ ] 未使用コード：定義されていないが使用されない変数/関数

#### SHOULD（Issue 化推奨）
- [ ] コメント不足：複雑なロジックに説明がない
- [ ] 型ヒント不足：型情報がない（Python 3.9+）
- [ ] 関数の責務が不明確
- [ ] マジックナンバー：説明のない定数

#### MAY（軽微）
- [ ] コードスタイル：スペース・インデントの不統一
- [ ] 冗長な式：より簡潔に書ける

**レビュー方法**:
```bash
wc -l main.py  # 行数確認
grep -n "^def " main.py | head  # 関数一覧
grep -n "TODO\|FIXME" main.py  # マーカーチェック
```

---

### 4. テスト

**観点**: テストが十分か

#### MUST（Issue 化必須）
- [ ] テストが落ちている：CI が失敗
- [ ] テストカバレッジ不足：新機能にテストがない（< 80%）
- [ ] テストが形骸化：常に成功する無意味なテスト

#### SHOULD（Issue 化推奨）
- [ ] エッジケースのテストがない
- [ ] エラーハンドリングのテストがない
- [ ] 統合テストの不足

**レビュー方法**:
```bash
python3 -m unittest
python3 -m coverage run -m unittest
python3 -m coverage report
```

---

### 5. ドキュメント

**観点**: ドキュメントが最新か、適切か

#### MUST（Issue 化必須）
- [ ] README が古い：手順が実装と異なる
- [ ] API ドキュメント不在：新しい関数/エンドポイント
- [ ] 環境変数ドキュメント不完全

#### SHOULD（Issue 化推奨）
- [ ] セットアップ手順が不明確
- [ ] トラブルシューティングがない
- [ ] 図や例が不足

**レビュー方法**:
```bash
grep -n "GEMINI_API_KEY\|GCS" README.md  # 環境変数チェック
diff <(grep "def " main.py) <(grep "^##" README.md)  # 新機能の記載確認
```

---

### 6. パフォーマンス

**観点**: パフォーマンス問題がないか

#### MUST（Issue 化必須）
- [ ] 無限ループ：CPU が 100%
- [ ] メモリリーク：メモリが増え続ける
- [ ] N+1 クエリ：ループ内でクエリ実行

#### SHOULD（Issue 化推奨）
- [ ] 不必要なループ：O(n²) 以上の複雑性
- [ ] 大量データ処理時のメモリ溢れ

**レビュー方法**:
```bash
python3 -m cProfile -s cumtime main.py  # プロファイリング
```

---

### 7. 依存関係・環境

**観点**: 外部依存が適切か

#### MUST（Issue 化必須）
- [ ] サポート外のバージョン：Python 3.8 以下
- [ ] セキュリティアップデートの未適用
- [ ] 未宣言の依存関係

#### SHOULD（Issue 化推奨）
- [ ] バージョン指定が不明確：requirements.txt に "==X.X.X" がない
- [ ] 非推奨パッケージの使用

---

### 8. 環境変数・設定

**観点**: 設定管理が適切か

#### MUST（Issue 化必須）
- [ ] 秘密情報のハードコード：API キーが直接記載
- [ ] 設定ドキュメント不足
- [ ] 環境依存のコード：本番/開発で異なる動作

#### SHOULD（Issue 化推奨）
- [ ] デフォルト値の妥当性
- [ ] 設定項目のバリデーション不足

**レビュー方法**:
```bash
grep -n "API_KEY\|SECRET\|PASSWORD" main.py
grep -n "os.environ" main.py
```

---

### 9. 破壊的変更（Breaking Changes）

**観点**: 既存クライアント・デプロイメントに互換性があるか

#### MUST（Issue 化必須）
- [ ] 環境変数が削除：既存設定が無視される
- [ ] API レスポンス形式が変更：クライアント互換性喪失
- [ ] エンドポイント削除：既存クライアントが失敗
- [ ] パラメータ必須化：既存呼び出しが失敗

#### SHOULD（Issue 化推奨）
- [ ] デフォルト値が変更：暗黙の挙動が変わる
- [ ] 戻り値の型が変更：互換性に注意
- [ ] 関数シグネチャの変更：呼び出し側が対応必要

**レビュー方法**:
```bash
# 環境変数の削除チェック
git diff main HEAD -- main.py | grep -E "os\.environ|config"

# エンドポイントの変更チェック
git diff main HEAD -- main.py | grep -E "@app\.(get|post|delete)"
```

---

### 10. デッドコード・未使用定義

**観点**: 使用されていないコードが存在しないか

#### MUST（Issue 化必須）
- [ ] 関数が定義されているが呼び出されない
- [ ] 変数が定義されているが参照されない
- [ ] インポートが存在するが使用されない
- [ ] 削除されたエンドポイントの残骸

#### SHOULD（Issue 化推奨）
- [ ] 到達不可なコード：if-else で片方だけ実行可能
- [ ] 無条件 return 後のコード
- [ ] デバッグコードが残っている

**レビュー方法**:
```bash
# 未使用インポート検出
python3 << 'EOF'
import ast
import sys

with open('main.py', 'r') as f:
    tree = ast.parse(f.read())

# 未使用の変数/関数を検出
EOF

# grep で TODO/FIXME を検出
grep -n "TODO\|FIXME\|DEBUG" main.py
```

---

### 11. ログ・観測性（Observability）

**観点**: 動作をトレース・デバッグできるか

#### MUST（Issue 化必須）
- [ ] 重要なイベントのログがない：エラーが追跡不可
- [ ] ログレベルが不適切：DEBUG と INFO の混在
- [ ] 本番環境でデバッグログが出力：パフォーマンス低下

#### SHOULD（Issue 化推奨）
- [ ] トレースID/相関ID がない：リクエスト追跡不可
- [ ] ログ出力が不均一：一部の処理だけログがある
- [ ] エラーコンテキストが不足：原因特定が困難

**レビュー方法**:
```bash
# ログ出力の確認
grep -n "logger\.\|print(" main.py | head -20

# logging レベルの確認
grep -n "logger\.\(debug\|info\|warning\|error\)" main.py
```

---

### 12. API 設計・インターフェース

**観点**: API が一貫性・予測可能性を持つか

#### MUST（Issue 化必須）
- [ ] エラーレスポンス形式が不統一
- [ ] ステータスコードが不適切
- [ ] パラメータ名が不統一

#### SHOULD（Issue 化推奨）
- [ ] エラーメッセージが不明確
- [ ] API ドキュメントが不完全
- [ ] バージョニング戦略がない

**レビュー方法**:
```bash
# エンドポイント定義の確認
grep -n "@app\.\(get\|post\|delete\)" main.py

# HTTPステータスコードの確認
grep -n "HTTPException\|status_code" main.py
```

## 📊 Issue 化の判断基準

| 観点 | MUST 条件 | SHOULD 条件 | MAY 条件 |
|------|----------|-----------|---------|
| **機能性** | テスト失敗 | エッジケース未対応 | 最適化の余地 |
| **セキュリティ** | 脆弱性あり | 暗号化不足 | 権限管理改善 |
| **品質** | 規約違反 | コメント不足 | スタイル |
| **テスト** | テスト落ち | カバレッジ < 80% | エッジケース不足 |
| **ドキュメント** | 情報が古い | 説明が不明確 | 例が少ない |
| **パフォーマンス** | メモリリーク | N+1 クエリ | 最適化余地 |
| **依存関係** | セキュリティ更新未適用 | バージョン指定なし | 非推奨パッケージ |
| **破壊的変更** | 環境変数削除 | デフォルト値変更 | 型の微妙な変更 |
| **デッドコード** | 呼び出されない関数 | 到達不可なコード | デバッグコード残存 |
| **ログ・観測性** | 重要なログ欠損 | トレースID がない | ログ出力が不均一 |
| **API 設計** | ステータスコード不適切 | エラーメッセージ不明確 | ドキュメント不完全 |

## 🔄 レビュー実行プロセス

### ステップ 1: 自動レビュー実行

```bash
/code-review main HEAD
```

### ステップ 2: 結果分析

各指摘に対して以下を確認：
1. **重大度**: MUST/SHOULD/MAY のいずれか
2. **根拠**: 上記の観点に該当するか
3. **偽陽性**: 実際に問題か、false positive でないか
4. **修正方針**: どう修正するか

### ステップ 3: Issue 作成

重大度が MUST/SHOULD の場合、Issue を作成：

```bash
gh issue create \
  --title "[Review] Issue title" \
  --label code-review \
  --body "$(cat .github/ISSUE_TEMPLATE/code-review.md)"
```

### ステップ 4: 修正・追跡

Issue に対応：
```bash
git checkout -b fix/issue-#123
# 修正実装
git commit -m "fix: Resolve code review issue #123"
git push origin fix/issue-#123
```

### プロンプト例

```
以下の観点でコードレビューを実行してください：
1. 機能性・正確性
2. セキュリティ
3. コード品質

MUST 指摘を見つけたら Issue テンプレートを使って Issue を作成してください。
各 Issue に以下を含めてください：
- 問題と判断した内容
- 判断の根拠（何をチェックした）
- 偽陽性の判断
- 修正方針の案
```

## 📝 チェックリスト

レビュー実行前に確認：

- [ ] レビュー観点が明確か
- [ ] テスト環境が整備されているか
- [ ] ドキュメントが最新か
- [ ] セキュリティツールが利用可能か

レビュー結果から Issue 作成前に確認：

- [ ] 同じ指摘が重複していないか
- [ ] 偽陽性の可能性を記載したか
- [ ] 修正方針が実現可能か
- [ ] 重大度の判定が正確か
