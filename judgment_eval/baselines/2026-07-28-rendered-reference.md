## 読み方

**言えること** — ルーブリック（`symbols.json` の特徴文）と AND 判定の組み合わせは、
理想解答に対しては壊れていない。「文の書き方が悪くて理想解答すら落ちる記号」は
現時点で 1 つも無い。下限は clear。

**言えないこと** — これは手描き精度ではない。ケースが全て `ref_svg` の描画である
以上、線の歪み・かすれ・比率のズレに対する頑健性は一切測れていない。実際の
偽 NG 率はこれより必ず悪くなる。**0.0% は手描き精度の楽観的な上界**であって、
実力値ではない。

**測れていないこと** — 偽 OK 率の母数が 0。誤った解答のケースがまだ 1 件も無いため、
「間違えているのに通る」方向は完全に未検証。`common_mistakes` を描き起こした
ケースを入れるまで、この欄は埋まらない。

## 測定中に見つかった別の問題

全 54 判定で、`primary`（無料枠）キーが `400 INVALID_ARGUMENT — API key not valid`
を返し、毎回 paid キーへフォールバックして成功していた。

原因はローカル `.env.local` の `GEMINI_API_KEY` の先頭に `y` が 1 文字余分に付いて
いたこと（`yAQ.…` / 54 文字。正しくは `AQ.…` / 53 文字）。1 文字消すと同じキーが
通ることを確認済み。レート制限（429 / `RESOURCE_EXHAUSTED`）ではない。

一文字の打ち間違いで済む話ではあるが、症状の出方に問題がある：

- 1 判定あたり 2 回（primary × 2 モデル）の無駄な往復が発生している
- 「無料枠 → 有料枠」のコスト最適化が実質機能しておらず、全て課金側に流れている
- `_generate_vision_result` は 400 を一時的な失敗と同じ扱いで握りつぶすため、
  **恒久的な設定ミスがログ上は一時障害と見分けられない**。`/readyz` も
  レート制限状態しか見ないので OK を返し続ける

つまり「打ち間違えたキーを本番に入れても、誰も気づけない」。フォールバック先が
生きている限りサービスは動き続け、コストだけが静かに課金側へ寄る。

本番は Secret Manager 管理なのでローカルと同一とは限らない。要確認。
キー自体の修正はハーネスとは別件として扱うこと。
